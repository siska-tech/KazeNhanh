### **🎯 目的**

* ライブラリの品質を保証するためのテスト戦略と具体的なテストケースを定義する。  
* バグの早期発見とデグレード（意図しない機能低下）の防止を目的とする。

### **1\. テスト方針 (Test Policy and Strategy)**

本セクションは、KazeNhanhライブラリの品質属性を定義し、それを達成および保証するための戦略的アプローチを規定する。

#### **1.1. 品質目標 (Quality Attributes)**

本ライブラリは、その名称「KazeNhanh」（「速い風」の意）が示す通り、卓越したパフォーマンスを中核的な価値として設計されている。したがって、本ライブラリの品質目標は、以下の優先順位で定義される。

* **Q1 (最優先): パフォーマンス (Nhanh \- 速さ)**  
  * 要件定義書で指定されたレイテンシ（p99）およびスループット（RPS）のKPIを、いかなる状況でも下回らないこと。  
  * アーキテクチャ上の決定として、\*\*「機能が正しくとも、定義されたKPIを満たせないほど遅い場合は、機能不全と同等、あるいはそれ以上の深刻度（Severity）を持つバグ」\*\*として扱う。パフォーマンステストは、本仕様書において最も重要な検証項目である。  
* **Q2: 正確性 (Correctness)**  
  * APIは設計書通りの入出力を厳密に保証すること。  
  * 保存されたデータが、いかなる操作（並行アクセス、メモリ駆逐、TTL失効）によっても破損しないこと。  
  * TTL（Time To Live）が指定された期間（または即時）に正確に動作し、失効したデータが返されないこと。  
* **Q3: 堅牢性 (Robustness) & 耐障害性 (Resilience)**  
  * 高負荷、メモリ限界（OOM）、ネットワーク分断（該当する場合）、および想定外の異常な入力（ファジング）においても、ライブラリがパニック（クラッシュ）しないこと。  
  * ライブラリの呼び出し元（アプリケーション）をクラッシュさせてはならない。  
  * リソースリークが絶対に発生しないこと。特に、長時間稼働（数週間～数ヶ月）を前提とし、ゴルーチンリーク、メモリリーク、ファイルディスクリプタのリークは許容されない。  
* **Q4: 並行性 (Concurrency)**  
  * 本ライブラリは、マルチスレッド（Go言語におけるマルチゴルーチン）環境での高並行アクセスが前提である。  
  * いかなる同時アクセスパターンにおいても、データの一貫性が保証されること（レースコンディションの不在）。  
  * 複数のゴルーチンによる同時操作でデッドロックが発生しないこと。

#### **1.2. テスト種別とスコープ (Test Types and Scope)**

上記の品質目標（Q1-Q4）を網羅的に検証するため、以下のテスト種別を定義し、実施する。

* **1.2.1. 単体テスト (Unit Test)**  
  * **スコープ:** 内部モジュール（詳細設計書に基づく）。  
  * **目的:** 外部から隠蔽された内部コンポーネントのロジックを検証する（ホワイトボックステスト）。  
  * **対象例:** EvictionPolicy（LRU/LFUロジック）、Serializer（直列化/復元ロジック）、ShardedMap（ハッシュ分散ロジック）、TTLManager（失効管理ロジック）。  
* **1.2.2. 結合テスト (Integration Test)**  
  * **スコープ:** 公開APIインターフェース（API設計書に基づく）。  
  * **目的:** ライブラリをブラックボックスとして扱い、公開APIのエンドツーエンドの動作（Set, Get, Delete 等）が要件を満たすか検証する。  
  * **詳細:** 本仕様書の「3. テストケース」の大部分を占める。  
* **1.2.3. パフォーマンステスト (Performance Test)**  
  * **スコープ:** Q1（パフォーマンス）で定義された非機能要件。  
  * **目的:** レイテンシ、スループット、スケーラビリティ、リソース効率のKPIを測定し、合否を判定する。  
  * **構成:** ベンチマークテスト、ストレステスト（限界負荷）、ソークテスト（長時間耐久）を含む。  
* **1.2.4. 並行性テスト (Concurrency Test)**  
  * **スコープ:** Q4（並行性）。  
  * **目的:** データ競合（Race Condition）およびデッドロックを検出する。  
  * **実施:** Go言語のレースディテクタ（-race フラグ）を常時有効にして、単体テストおよび結合テストの全スイートを実行する。加えて、3.5章で定義する高並行状態を意図的に引き起こす専用テストケースを実施する。  
* **1.2.5. ファズテスト (Fuzz Testing)**  
  * **スコープ:** Q3（堅牢性）。  
  * **目的:** 想定外の入力（ランダムなバイト列、異常な長さのキー、破損したシリアライズデータ）を与え、ライブラリがパニックや未定義の動作を起こさないことを検証する。  
  * **ツール:** Go 1.18以降のネイティブファジング、または go-fuzz を使用する。

#### **1.3. 品質メトリクスとカバレッジ目標 (Quality Metrics)**

リリース判定の客観的基準として、以下の品質メトリクスを定義する。これらの目標値は、リリースのための\*\*必須条件（Non-Negotiable）\*\*である。

* **コードカバレッジ (Code Coverage)**  
  * **C0（ステートメント網羅率）: 95% 以上**  
  * **C1（分岐網羅率）: 90% 以上**  
  * C1（分岐網羅）の目標値を高く設定する理由は、高性能ライブラリのコアロジックはエラーハンドリングやエッジケースの分岐が複雑になりがちであり、C1の網羅率が低いことは、異常系の考慮漏れ、すなわち堅牢性（Q3）の欠如に直結するためである。  
* **APIカバレッジ (API Coverage)**  
  * API設計書に記載された全エンドポイント（正常系・異常系・境界値）のテストケース網羅率: **100%**  
* **パフォーマンスKPI (Performance KPI)**  
  * 5.1章で定義する全パフォーマンスKPIの達成率: **100%**  
* **不具合メトリクス (Bug Metrics)**  
  * リリース判定時において、S1（深刻度: 最高）およびS2（深刻度: 高）のオープンな不具合が **0件** であること。

#### **1.4. 採用テストフレームワークとツールスタック**

テストの効率性、再現性、および網羅性を担保するため、以下のツールスタックを採用する。

* **言語:** Go (v1.21.x および v1.22.x)  
* **単体・結合テスト:** testing (Go標準パッケージ), stretchr/testify (Assertion/Mocking), testcontainers-go (依存コンポーネントのコンテナ管理、必要に応じて)  
* **並行性:** Go Race Detector (-race ビルドフラグ)  
* **パフォーマンス (ベンチマーク):** testing (Go標準 BenchmarkXxx 関数), pprof (プロファイリング)  
* **パフォーマンス (負荷生成):** vegeta (HTTPベースの場合), ghz (gRPCベースの場合), または本ライブラリ専用のカスタム負荷生成クライアント（TCP/UDPベースの場合）  
* **CI/CD:** GitHub Actions (または指定のCIツール)

### **2\. テスト環境 (Test Environment Specification)**

テスト結果の信頼性と再現性を担保するため、テスト実行環境を以下のように厳格に定義する。

#### **2.1. CI/CD実行環境 (PR/Merge-time)**

* **トリガー:** 全てのPull RequestおよびmainブランチへのMerge時  
* **OS:** Ubuntu 22.04 (GitHub Actions hosted runner)  
* **Goバージョン:** マトリックステスト (1.21.x, 1.22.x)  
* **実行内容:**  
  1. go vet (静的解析)  
  2. go mod tidy (依存関係の整合性)  
  3. go test./... (単体テスト \+ 結合テスト)  
  4. go test \-race./... (並行性テスト)  
  5. go run./tools/coverage.go (カバレッジレポート生成と 1.3章のメトリクス判定)

#### **2.2. パフォーマンステスト（"Nhanh" 検証）環境**

Q1（パフォーマンス）の検証は、他のプロセスによるリソース競合（「ノイジー・ネイバー」問題）の影響を受ける共有CIランナーで実行してはならない。これは、測定結果の信頼性を著しく損なうため、**アーキテクトとしての要求として禁止**する。

パフォーマンステストは、以下の専用かつ隔離された環境で実施されなければならない。

* **トリガー:** mainブランチへのMerge後（自動）、およびリリースタグ払い出し時（必須）  
* **インフラ:** AWS (またはGCP/Azure) の専用VPC内  
* **SUT (System Under Test) マシン:**  
  * **インスタンスタイプ:** c6gn.xlarge (または同等のコンピューティング最適化、高ネットワーク帯域インスタンス)  
  * **OS:** Amazon Linux 2023 (または指定のディストリビューション)  
  * **環境:** Dockerコンテナ (リソース制限: CPU 4コア, メモリ 8GiB)  
* **負荷生成クライアント (Load Generator):**  
  * **インスタンスタイプ:** c6gn.xlarge (SUTと同等かそれ以上)  
  * **ツール:** 5.1章で定義された負荷生成クライアント  
  * **配置:** SUTとは**物理的に異なるインスタンス**に配置する。これにより、クライアントとSUT間の実ネットワークレイテンシを含めた、より現実的なパフォーマンス測定が可能となる。  
* **ネットワーク:**  
  * 同一アベイラビリティゾーン（AZ）内、低レイテンシネットワーク構成。  
* **厳格な要件:**  
  * この環境構成は、Terraform等のIaC (Infrastructure as Code) ツールによってバージョン管理され、常に同一の「ベースライン環境」で計測されなければならない。  
  * 計測結果はダッシュボード化され、過去のmainブランチのコミット（ベースライン）とのリグレッション（性能低下）が自動的に比較されること。

#### **2.3. テストデータ管理**

* **単体・結合テスト:**  
  * テストコード内で動的に生成・破棄されることを原則とする。ハードコードされた静的データは、ロジックの検証に不可欠な場合を除き使用しない。  
  * t.Cleanup() 等のGo標準機能を用い、テスト終了時にリソースがクリーンアップされることを保証する。  
* **パフォーマンステスト:**  
  * **キー:** 16〜256バイトのランダム文字列。キーの分布は、テストケースに応じて均等分布、または現実のワークロードを模した偏りのある分布（例: Zipf分布）をシミュレートする。  
  * **バリュー:** 1KB〜1MBの範囲で、テストケースごとに定義されたサイズのランダムペイロード（例: JSON, バイナリ）。データの圧縮率（ランダム度）も考慮する。

### **3\. テストケース: 結合テスト (APIレベル)**

### **4\. テストケース: 単体テスト (モジュールレベル)**

詳細設計書で定義された内部コンポーネントのロジックを検証する。これは、ライブラリの安定性とパフォーマンスの根幹をなすため、APIテストと同様に重要である。

#### **4.1. core.EvictionPolicy (例: LRU \- Least Recently Used)**

* **目的:** キャッシュが最大容量に達した際の、駆逐（Eviction）ロジックの正しさを検証する。

| ID | テスト項目 | テスト条件（入力） | 期待結果 |
| :---- | :---- | :---- | :---- |
| UNIT-EVI-001 | LRU 基本動作 | 容量=2。Add("k1") → Add("k2") → Add("k3") を実行。 | k1 (最も古く使われていない) が駆逐される。k2, k3 が残る。 |
| UNIT-EVI-002 | LRU 最近傍利用 (Get) | 容量=2。Add("k1") → Add("k2") → NotifyAccess("k1") (Get時に呼ばれる) → Add("k3") を実行。 | k1 が MRU に昇格するため、k2 が駆逐される。k1, k3 が残る。 |
| UNIT-EVI-003 | 削除された要素 | 容量=2。Add("k1") → Add("k2") → NotifyDelete("k1") → Add("k3") を実行。 | k1 は既に存在しないため、駆逐は発生しない。k2, k3 が残る。 |
| UNIT-EVI-004 | 上書きされた要素 | 容量=2。Add("k1") → Add("k2") → NotifyAccess("k1") (Set上書き時に呼ばれる) → Add("k3") を実行。 | k2 が駆逐される。k1, k3 が残る。 |

#### **4.2. core.ShardedMap (内部データ構造)**

* **目的:** 並行性向上のための内部データ構造（例: 32個のshardを持つsync.Mapまたはsync.RWMutexで保護されたmap）のハッシュ分散とロック競合のテスト。

### **6\. テスト実行と不具合管理**

#### **6.1. テスト実行サイクルとCI連携**

* **Pull Request (PR) 時:**  
  * **実行内容:** 2.1章の全テスト（go vet, go test./..., go test \-race./..., カバレッジ）を実行。  
  * **判定:** 全テストのPassと、カバレッジ目標 (1.3章) の維持をGitHub Actionsの**必須チェック (Required Check)** とする。  
* **Merge to main (Staging) 時:**  
  * **実行内容:** PR時テストに加え、2.2章の専用環境でパフォーマンステスト (5章) の全スイートを自動実行。  
  * **判定:** パフォーマンスのデグレード（例: ベースライン比でp99レイテンシが10%以上悪化、またはスループットが5%以上低下）を自動検知する。デグレードが検知された場合、ビルドを**失敗**させ、アーキテクトにアラートを通知する。  
* **Release Tag (Production) 時:**  
  * **実行内容:** Merge to main と同様の全テストスイートを最終実行する。  
  * **判定:** 6.3章のリリース判定基準に基づき、全項目がグリーンであることを確認する。

#### **6.2. 不具合の優先度 (Priority) と深刻度 (Severity)**

* **深刻度 (Severity):** 影響の大きさ  
  * **S1 (最高):** データ破損、データ喪失、パニック（クラッシュ）、レースコンディション、デッドロック、セキュリティ脆弱性、**パフォーマンスKPIの重大な未達 (例: 50%以上の悪化)**。  
  * **S2 (高):** **パフォーマンスのデグレード (10%～50%)**、APIの非互換、主要機能の不具合（例: TTLが効かない）、リソースリーク。  
  * **S3 (中):** マイナーな機能不具合（例: 特定の境界値でのエラーメッセージが不正確）、ドキュメントとの乖離。  
  * **S4 (低):** 誤字、 cosmeticな問題。  
* **優先度 (Priority):** 対応の緊急度  
  * **P1 (最高):** 即時修正が必要（リリースブロッカ）。  
  * **P2 (高):** 次のリリースまでに修正が必要。  
  * **P3 (中):** スケジュール内で対応。  
  * **P4 (低):** バックログ（対応未定）。

#### **6.3. リリース判定基準 (Release Criteria)**

以下の全条件を満たした場合にのみ、KazeNhanhライブラリの新規バージョンリリースを承認する。

1. CI/CDの全テストスイート (Unit, Integration, Concurrency, Performance) が 100% Pass していること。  
2. 品質メトリクス (1.3章) の全目標値（C0/C1カバレッジ、APIカバレッジ、全パフォーマンスKPI）を達成していること。  
3. 登録された不具合のうち、**S1 および S2 のオープンな不具合が0件**であること。  
4. S3 の不具合が許容範囲内であると、アーキテクトおよびプロダクトオーナーがレビューし、リリースを合意していること。
